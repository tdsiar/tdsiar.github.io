LLM Inference Engine in C

C · Aug 2026 to Present

What it is

Andrej Karpathy's llama2.c runs a Llama 2 style language model in one C file, run.c, about 1,000 lines long. I rebuilt it from an empty file as myrun.c (568 lines), without copying, to learn what inference does at the level of memory and arithmetic. That is the work an AI chip has to do in hardware.

The test model is stories15M: 15 million parameters, trained on short children's stories.

How it works

  1. Load the weights. Read the model's config header, then compute each weight matrix's size from it and read the matrices out of one flat file of floats, one allocation each. (The reference maps the file into memory instead.)
  2. Load the tokenizer. Read 32,000 vocabulary pieces and their scores.
  3. Run the forward pass for each token. Look up the token's embedding. Then, for each layer: RMS normalization, the query, key, and value matrix multiplies, rotary position encoding, attention over the cached keys and values, the output projection, and the feed forward block. The last step turns the final vector into 32,000 logits, one score per possible next token.
  4. Pick the next token. Greedy sampling takes the highest logit.
  5. Decode. Turn the token id back into text, including byte fallback tokens such as <0x0A> for a newline.

How I checked it

I used a golden master test. Both programs run greedy decoding on the same model, and diff compares the outputs:

./myrun stories15M.bin > mine.txt
./run   stories15M.bin -t 0 > ref.txt
diff mine.txt ref.txt

The generated story is identical, character for character. I also compared raw logits at 15 separate steps. They agree to 5 or 6 decimal places.

A bug found by bisection

At one point my story drifted from the reference at a single word. I bisected with the token count and found the first difference at step 19: my engine picked token 322, the reference picked 297.

Then I printed my logits at that step. They matched the reference (18.970549 against 18.970541), so the forward pass was correct. The only code between a correct logit and a wrong choice was the sampler. The cause was int max_p: an integer holding a float. It cut 18.97 down to 18, so a smaller value (18.29) compared as larger and won. The same line had a second bug: it stored a value where an index belonged. The bug stayed hidden for 19 steps because the truncation only mattered when the top two logits shared a whole number part.

Where it stands

The output matches the reference. Next steps: free all memory (checked with leaks), add error checks on file and memory calls, then measure tokens per second and memory use. After that, a roofline analysis of where the time goes, and a simple cycle level model of how the same work would run on dedicated hardware.

What I learned

  • How a transformer turns weights in memory into the next token, one matrix multiply at a time.
  • Golden master testing, bisection, and lldb for finding where two programs first disagree.
  • To check the instrument before I trust its reading, and to predict a value before I run the code.
  • To keep an index and a value apart. That mistake cost me more time than any other bug.
